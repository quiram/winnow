# Contributing to winnow

This document is for people working on winnow itself. If you just want to use it, see the [README](README.md).

## Repo layout

```

.claude-plugin/marketplace.json           # generated by `apm pack` — committed, consumed by APM & Claude Code

  create-tasks/SKILL.md
```

## Public and private skills

Winnow ships nine skills, but only six of them are meant to be called by name:

- **Public** — `winnow`, `update-context`, `create-tasks`,
  `transcribe-audio`, `listen-to-meeting`, `setup-winnow`. These are what the
  README documents.
- **Private** — `winnow-setup-context`, `winnow-setup-tracker`,
  `winnow-setup-audio`. Parts of `setup-winnow`, documented here and nowhere
  else.

Nothing enforces the split; a skill is a skill. What keeps it honest is the
`description`, which is what an agent matches against: each private part's
description names the skills that delegate to it, and points anyone asking to
"set up winnow" at `setup-winnow`. The README doesn't name them, and neither does the package
description in `apm.yml`, because both document how to use winnow rather than
how it works.

The parts exist because each prerequisite has two callers, not one.
`setup-winnow` settles everything up front — but users skip setup, so
`update-context` needs the same doc-map fix path when it finds no map, and
`create-tasks` the same tracker discovery when it finds no tracker. One skill
each, reached from both sides, keeps those rules in a single place.

That delegation is a name lookup, unlike the relative-path import described
below, and it fails softly: an agent that cannot find the part says so. Each
delegation point still states the outcome it needs in a sentence, so a skill
that cannot reach its part halts on a precise gap instead of improvising a
documentation structure or a tracker.

## The cross-skill engine dependency

`listen-to-meeting/scripts/listen.py` imports `Transcriber`, `StreamSegmenter`
and `model_is_cached` from `transcribe-audio/scripts/transcribe.py` — across a
skill boundary, by relative path. This looks unclean and is worth understanding
before anyone "fixes" it.

It is deliberate, for two reasons:

1. **The engine belongs to transcribe-audio.** listen-to-meeting captures audio
   and batches text; all audio-level work — VAD, utterance finalization,
   transcription — is transcribe-audio's job. Duplicating the engine would fork
   it; importing it keeps one implementation.
2. **There is nowhere else to put it.** APM's unit of distribution is the
   primitive. A package-level shared directory does not survive `apm pack`:
   under `includes: auto` a root `lib/`, `scripts/` or `common/` is silently
   dropped from the bundle, and naming one in an explicit `includes:` list fails
   outright with `Explicit include path is not a packable primitive`. That holds
   even for `scripts/`, which APM's own package-anatomy docs list as an authored
   directory. Claude Code *does* offer `${CLAUDE_PLUGIN_ROOT}` for exactly this,
   but winnow ships through both ecosystems and stays assistant-neutral, so a
   Claude-only mechanism is not available to us.

So the engine lives in the skill that owns it, and the other skill reaches for
it. Winnow already works this way one layer up: `winnow-setup-audio/SKILL.md`
drives `<listen-to-meeting-skill-dir>/scripts/listen.py`.

What this costs, and how it is contained:

- **The two skills must ship and install together.** `listen.py` resolves the
  engine through `load_engine()`, which fails with an actionable message — not a
  bare `ImportError` — when it is absent, unimportable, or too old to carry the
  API.
- **The imported names are a contract.** Changing the signature of `Transcriber`
  or `StreamSegmenter` is a breaking change to listen-to-meeting, not a local
  refactor. `transcribe.py`'s docstring says so.
- **The shared dependency pins are duplicated.** `faster-whisper`, `av` and
  `numpy` appear in both PEP 723 headers and are kept in step by hand; both
  blocks carry a comment saying so. Nothing enforces it.
- **`av` is capped below 19 on purpose.** faster-whisper only requires `av>=11`,
  so uv resolves the newest `av`, but faster-whisper 1.2.1 passes
  `metadata_errors` to `av.open()`, which `av` 19 removed. File transcription
  then crashes with a `TypeError` (`av` 16.1 to 18 are fine). Raise the cap only
  once a faster-whisper release supports the newer `av`. `transcribe.py check`
  decodes a second of generated audio, so it fails on a combination like this
  instead of passing and leaving the crash for the first real transcription.

If the engine ever gains a third consumer, revisit this: extracting it to a
published Python package, declared as a normal dependency in each script's PEP
723 header, is the clean answer that APM's model actually supports.

## Speaker attribution without diarization

`listen-to-meeting` does not identify speakers. It captures the microphone
(**Me**) and the system audio (**Others**) as two separate channels and treats
a switch between them as the signal that someone else is now talking.

That is deliberate. WhisperX can diarize, but it requires the user to accept a
model licence before it will run, and a prerequisite that cannot be settled by
`setup-winnow` on the user's behalf does not belong in a pipeline meant to work
out of the box. The channel split costs nothing to set up and is enough for the
skill's purpose, which is to catch inconsistencies and gaps, not to minute who
said what.

## The run log

Decisions made in a run, including the decision not to act on something, vanish with the conversation: the proposal is deleted once applied, and the AI context and tracker only hold what was approved. The run log, step 7 of `winnow`, is the opt-in answer for projects that want that trail. It is off by default so no project gains files it never asked for, which is why it is the one exception to the footprint-free objective.

Two decisions are worth knowing before changing it:

- **`winnow` writes it, not `update-context`.** The log covers tasks as well as context updates, and `update-context` should know nothing about tasks. Handing it the log would couple it to `create-tasks`' territory.
- **It is written between `create-tasks` and `update-context`.** `update-context` is the skill that offers to commit, so the log has to be in the working tree before it runs, or it would miss that commit. Running `create-tasks` first lets the log carry ticket links and record a task that failed. The two application skills are peers, so this order costs nothing. What remains is that context updates are logged as approved for execution, not as applied.

It deliberately holds no raw transcript or other source material (it points at sources instead), and winnow keeps no index of the logs folder; that is the project's call.

## Committing context updates

`update-context` ends by offering to commit, which is its Step 7. A context update that stays in the working tree is invisible to everyone else and to whatever work comes next, so leaving the commit to chance means approved knowledge quietly never lands. The skill therefore always makes the offer, but only as an offer: it never commits, pushes or opens a PR unprompted.

How it offers is the policy:

- **The project's own rules win.** If the AI context says how commits, branches and PRs work, the skill follows that, even where it permits committing straight to the default branch.
- **The fallback is a branch and a PR, never a direct push to the default branch.** Winnow is used by teams, and direct pushes to the default branch are not good practice for teams, so the skill does not nudge anyone towards them. It only suggests one when the project's context or the user does.
- **The offer covers the whole run.** `update-context` is the last step of the pipeline, so it also sweeps in what winnow left in the working tree, such as the [run log](#the-run-log), which keeps the log and the context changes in a single commit. Unrelated changes already in the tree are flagged and left out.

## Working with mill

[mill](https://github.com/quiram/mill) is a development dependency of this repo, not of the package: it sits under `devDependencies` in `apm.yml`, so people who install winnow never receive it. It exists so that contributors can use mill's `start-task` skill when beginning work here.

Its skills are deployed into `.claude/skills/` and committed, so a fresh checkout has them without running `apm install`. Treat those directories as generated: change them upstream in mill, never in place. The dependency is pinned to a tag in `apm.yml`; to move to a newer mill, change the tag and run `apm install`, then commit the updated `apm.lock.yaml` and deployed skills together.

## Releasing

Releasing is handled by the repo-local `release` skill: with a coding agent, ask it to "release version X.Y.Z". The skill lives at [.claude/skills/release/SKILL.md](.claude/skills/release/SKILL.md) — it is not part of the winnow package — and doubles as the manual step-by-step instructions if you're releasing by hand.
